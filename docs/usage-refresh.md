# 用量刷新机制与回归用例

## 刷新规则

| 状态 / 事件 | 默认行为 |
|---|---|
| 官方窗口位于前台 | 每 30 秒读取一次 |
| 窗口可见但位于后台 | 每 60 秒读取一次 |
| 最小化、隐藏到托盘、找不到窗口 | 每 300 秒读取一次，已启动的连接继续复用 |
| 切回前台、恢复窗口、系统唤醒 | 1 秒防抖后补刷，多个触发合并 |
| 托盘「立即刷新」 | 已有请求时复用，否则立即读取，可跳过网络失败退避 |
| 读取失败 / 超时 | 30、60、120、240、300 秒退避，成功后恢复正常间隔 |
| 登录失效且自动恢复失败 | 自动恢复探测不短于 300 秒；切换焦点不会绕过该限制 |
| 监视器自身连接收到原生额度通知 | 账号确认后立即校验、显示，轮询仍保留 |
| 服务端返回的额度重置时间到达 | 重置时间后约 2 秒补刷；仍是旧窗口时约 10 秒后再确认一次 |

每轮通过 `account/read`（`refreshToken: false`）确认监视器连接的本地账号，再读取
`account/rateLimits/read`。前者不主动刷新令牌，不新增网络拦截、调试日志监听或常驻
辅助进程。额度优先使用 `rateLimitsByLimitId.codex`，兼容旧版 `rateLimits`。
前台、后台、最小化间隔分别由 `ForegroundRefreshSeconds`、`RefreshSeconds`、
`MinimizedRefreshSeconds` 配置。

正常情况下只保留一个有效读取；账号确认与额度读取共用 30 秒超时。超时后取消
本地跟踪，忽略迟到响应，并退避重试。这不代表已中止服务端正在处理的请求。
调度使用单调时钟，系统日期、时区调整不会改变轮询截止时间。

普通读取失败或超时后的重试使用独立截止时间，退避到期便可读取，不再等待后台
60 秒或最小化 300 秒的正常刷新周期，也不被焦点事件的防抖继续推迟。成功后恢复
当前窗口状态的正常周期。仍然合并正在进行的请求，登录失效后的自动探测保留
不短于 300 秒的限制。

重置时间补刷复用相同的调度器，失败退避、登录恢复限制和请求合并仍然有效。
每个额度窗口的重置时间最多触发两次读取；常规读取在该时间后完成也可覆盖补刷。
服务端返回新的重置时间，或确认用量在重置后下降时，取消旧窗口的补刷。
不会根据本地时钟直接把剩余额度改成 100%；连接超时、网络失败或服务端缓存仍可能
延迟确认。两个窗口同时重置会合并读取，切换账号清除旧账号的重置计划。

账号标识变化或自身连接收到 `account/updated` 时清除额度、重置券、更新时间及额度
校验状态。重置券异步结果按账号版本校验，旧版本的结果不再显示。账号指纹仅保留
在内存，不记录邮箱、账号标识或令牌。当前协议的账号邮箱可为空，也没有保证提供
稳定的工作区标识，因此不能自动证明监视器与官方界面属于同一账号、同一工作区。

桌面悬浮条的鼠标提示包含上次确认更新时间、重置券详情和刷新失败时的缓存说明。
失败或数据超过当前刷新周期的合理阈值时，提示还显示距上次成功确认的时间。
过期阈值为当前刷新间隔的两倍加 30 秒，且不短于 120 秒；最小化时按其较长周期
判断。成功获取相同百分比会刷新确认时间，并清除失败/过期状态。
窗口吸附模式鼠标穿透，可从托盘查看更新时间和失败提示。确认时间代表数据被接受
显示的时间，不代表官方客户端发出请求的时间，也不代表服务端额度计算时间。

这里的通知是监视器自己启动的 app-server 在 stdio JSON-RPC 连接上发送的
`account/rateLimits/updated`，不是官方客户端的请求或推送。即使该连接没有收到
通知，也会继续按上述间隔读取。官方界面与监视器仍可能短暂显示不同数据。

## 诊断日志与磁盘预算

正式默认 `DiagnosticsEnabled: false`，既有配置中的显式设置继续保留。排查时修改
程序目录下的 `settings.json` 为 `DiagnosticsEnabled: true`，重启监视器后生效。
日志仅写入本地 `%LOCALAPPDATA%\CodexRateMonitor\logs`，不自动上传。

- 默认保留 7 天（`DiagnosticRetentionDays` 可配置为 1–30 天），启动和运行期间
  每小时检查清理；关闭诊断后仍执行清理，程序退出后没有后台清理进程。
- 按 UTC 日期命名，单文件约 2 MiB 时轮转，所有 `usage-*.log` 合计预算 20 MiB。
  追加前若会超预算，则先删除最旧文件；无法删除且容量不足时停止追加。
- 每条日志限制字段长度，通知和错误不记录邮箱、令牌、错误原文或完整响应。
  错误分类为固定枚举，协议错误码仅保留可解析的数字；分类只是排查线索。

| 日志事件 | 用途 |
|---|---|
| `rate-refresh-started` | 读取周期 ID、连接版本、窗口状态、刷新原因 |
| `rate-refresh-completed` | 结果、包含账号确认的周期耗时、连续失败次数和退避秒数 |
| `account-request` / `rate-request` / `rate-response` | 用协议 ID 和周期 ID 对照请求与收包时间 |
| `account-response-error` / `rate-response-error` | 脱敏错误分类和数字错误码 |
| `rate-request-timeout` / `app-server-response-ignored` | 超时及被丢弃的迟到响应 |
| `rate-notification-received` | 确认连接确实收到了额度通知，含账号尚未确认时收到的通知 |
| `rate-notification` | 账号确认后的解析结果，准备交给数据显示校验 |
| `rate-notification-ignored` / `rate-notification-deferred` / `rate-notification-displayed` | 通知最终被忽略、暂缓或显示及原因 |
| `snapshot-displayed` | 实际显示时间、数据来源和对应 ID |

刷新原因包括 `periodic`、`focus`、`restore`、`resume`、`manual`、`retry`、
`reset_due`、`validation`、`startup`、`account` 和 `auth_probe`。

## 自动验证

```powershell
.\scripts\build.ps1 -OutputDirectory artifacts\CodexRateMonitor
.\scripts\test-usage-refresh.ps1 -MonitorPath artifacts\CodexRateMonitor\CodexRateMonitor.exe
.\scripts\test-auth-recovery-regression.ps1 -MonitorPath artifacts\CodexRateMonitor\CodexRateMonitor.exe
.\scripts\verify.ps1
```

刷新测试使用虚拟时钟和模拟 app-server，不访问真实账号或官方网络服务。它验证
请求数量、防抖、超时、三种窗口状态下独立到期的失败重试与成功恢复、迟到响应、连接复用、额度桶选择、账号切换、旧数据
清理、重置时刻补刷、缓存年龄及三种语言的托盘长度限制，以及通知日志、错误脱敏、
日志轮转、容量限制和关闭诊断后的清理。

## 手动验证

启用 `DiagnosticsEnabled` 后查看监视器日志中的 `rate-request`、`rate-response`、
`snapshot-displayed` 和超时记录。日志路径及配置方式见 README。

| 操作 | 预期结果 |
|---|---|
| 官方窗口前台停留 2 分钟 | 约每 30 秒读取；保持同一个监视器子进程 |
| 切换到其他程序 2 分钟 | 官方窗口仍可见时约每 60 秒读取 |
| 最小化官方窗口并等待 6 分钟 | 约每 300 秒读取 |
| 连续切换焦点后返回官方窗口 | 最后一次返回约 1 秒后补刷；没有并发请求堆积 |
| 恢复最小化窗口 / 电脑休眠后唤醒 | 约 1 秒后补刷；失败退避和登录失效限制仍有效 |
| 连续点击「立即刷新」 | 读取未结束时合并，完成后可发起下一次 |
| 临时断网后恢复 | 保留上次成功额度和时间，提示失败；成功后恢复正常周期 |
| 切换账号并等待监视器确认 | 旧额度、重置券和时间被清空，新账号较低用量立即接受 |
| 闲置且额度长时间不变 | 不因连续相同额度重启子进程 |
| 在重置时刻保持最小化 | 重置后约 2 秒补刷，旧窗口最多再确认一次；不自行生成 100% |
| 持续断网后恢复 | 悬停/托盘显示缓存年龄，成功确认后清除提示 |
| 对比官方界面和悬浮条 | 核对账号、剩余/已用口径、重置时间；记录两边截图及监视器更新时间 |

真实 Windows 休眠、账号切换及官方服务缓存需要按表操作验证；模拟测试不替代这些
外部行为的验证。CPU、内存与进程总网络流量也应在真实使用场景观察，不能从读取
次数推算整个 app-server 的网络开销。
